### Rubrica de Avaliação — Fase 3: Desenvolvimento Web, TDD e Versionamento (Projeto Integrador)

Esta rubrica foi estruturada para avaliar as entregas do **Marco 3** do Projeto Integrador (Técnico em Programador de Sistemas), alinhada aos pressupostos do **Modelo Pedagógico Senac (MPS)**. A avaliação analisa os aspectos técnicos da **Unidade Curricular 3 (UC3)** e a evidência das **Marcas Formativas Senac**, utilizando a escala de menções padrão: **A (Atendido)**, **PA (Parcialmente Atendido - com recuperação imediata)** e **NA (Não Atendido)**.

---

### 1. Matriz Avaliativa do Marco 3 (Aplicação Web, Pytest e GitHub)

| Critério de Avaliação | Indicador / Marca Formativa Mobilizada | A — Atendido (Domínio Pleno) | PA — Parcialmente Atendido (Necessita Ajustes) | NA — Não Atendido (Insuficiente) |
| :--- | :--- | :--- | :--- | :--- |
| **1. Arquitetura e Funcionalidade Web** | **Indicador UC3 / Domínio Técnico-Científico**: Elabora código e rotas web conforme requisitos e especificações da solução. | Endpoints/rotas web (Flask/Django) funcionam perfeitamente para CRUD, tratam exceções e integram-se ao banco de dados sem erros. | A aplicação funciona parcialmente; apresenta falhas pontuais em validações, rotas secundárias ou tratamento de erros. | A aplicação web não roda, apresenta erros fatais de execução ou não atende aos requisitos mínimos do projeto. |
| **2. Qualidade dos Testes Automatizados (TDD)** | **Indicador UC3 / Domínio Técnico-Científico**: Utiliza metodologias de teste automatizado (Pytest) para validar a aplicação. | Escreve suíte de testes unitários/integração com `pytest`, utiliza *fixtures/mocks* corretamente e atinge a meta de cobertura de código (\\(\ge 80\%\\)). | Escreve testes simples com `pytest`, mas a cobertura é baixa (\\(<50\%\\)) ou não utiliza *fixtures/mocks* para isolar dependências. | Não entrega testes automatizados ou a suíte de testes falha completamente ao ser executada no terminal. |
| **3. Gestão de Código e Versionamento** | **Indicador UC3 / Atitude Colaborativa e Autonomia Digital**: Opera ferramentas Git/GitHub para colaboração e publicação de código. | Repositório no GitHub organizado com histórico de *commits* claros, uso de *branches* para funcionalidades, sem conflitos e com Tag/Release marcada (`v1.0.0`). | Repositório criado no GitHub, porém com *commits* concentrados em poucas datas, sem uso de *branches* ou sem a marcação da Tag de versão. | Código não foi enviado ao GitHub ou repositório encontra-se desorganizado, incompleto ou inacessível. |
| **4. Alinhamento ao Desafio do PI** | **Indicadores do PI / Visão Crítica e Atitude Empreendedora**: Responde às necessidades do tema gerador com foco no cliente/comunidade. | A solução automatiza de forma efetiva a dor real da organização parceira, apresentando interface limpa, segura e utilizável. | O sistema resolve apenas parte do problema do cliente ou apresenta usabilidade confusa que dificulta a adoção prática. | O sistema desenvolvido não guarda relação com os requisitos levantados no tema gerador do Projeto Integrador. |

### 3. Orientações para Feedback e Recuperação Imediata no MPS

1. **Feedback Construtivo e Formativo:** Ao devolver a rubrica para a equipe, destaque primeiramente as evidências de **Domínio Técnico** e **Atitude Colaborativa** constatadas no GitHub.
2. **Plano de Recuperação Imediata (Para menções PA):** Conforme as diretrizes do MPS, a recuperação ocorre assim que a fragilidade é identificada. Se uma equipe obteve **PA** no critério de testes (Pytest), agende uma atividade prática de laboratório para que reestruturem a suíte de testes e elevem a cobertura antes do evento de Síntese (Fase 4).
